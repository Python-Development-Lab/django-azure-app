## Чому

AI PR Review на PR feat/finops-cost-export підняв питання: репозиторій
історично документований як "6-модульна структура" (network, key_vault,
database, app_service, monitoring, sarif_archive), а новий модуль
`cost_export` порушує цю інваріанту. AI прямо зазначив, що це рішення
не може ухвалити автор PR одноосібно — потрібен явний sign-off людини.

Рішення: приймаємо розширення до 7 модулів. `cost_export` вирішує
genuinely окрему задачу (Storage Account + RBAC для Cost Management
Export CSV-файлів), не пов'язану напряму з жодним із наявних шести
модулів. Найближчий кандидат для злиття — `monitoring` — семантично
про інший тип даних (діагностичні логи/метрики Sentinel, Application
Insights), не про cost-дані. Влиття `cost_export` туди дало б менш
чіткий, перевантажений модуль замість чистого поділу відповідальності.

"6-модульна структура" в документації/пам'яті проєкту варто читати як
опис стану на момент написання, не як жорстку стелю. Кожен новий
genuinely окремий concern — кандидат на власний модуль, якщо це не
призводить до невиправданого розростання (наприклад, окремий модуль
на кожен `azurerm_role_assignment` був би надмірним).

## Альтернатива

Розглядалась: влити storage account + RBAC для cost export у модуль
`monitoring`. Відхилено — `monitoring` вже містить Sentinel, Log
Analytics, Application Insights; додавання туди ще й Cost Management
Export storage розмило б його єдину відповідальність без реальної
економії (той самий обсяг Terraform-коду, лише переміщений в чужий
контекст).

Якщо в майбутньому з'явиться третій-четвертий "штучний" модуль
подібного розміру (кілька ресурсів для однієї вузької, ізольованої
задачі), варто переглянути: чи не час формалізувати підмодульну
структуру (наприклад, `modules/storage/cost_export`,
`modules/storage/sarif_archive`) замість плаского списку модулів
верхнього рівня.
